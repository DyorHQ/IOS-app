# DyorHQ security audit — 2026-09-26

Scope: the whole DyorHQ organization.
- **IOS-app**: the iOS app and DyorKit, the Next/vinext web app, the Cloudflare worker, Supabase migrations and Edge Functions, the Foundry contracts (Launchpad, Moments cohorts 1–3), scripts and CI.
- **website**, **docs** and **accounts-domain**: these three are report only.

Branch: `claude/kind-brown-1520k1` (base `7c79361`). Every fix in this report is a commit on that branch. Nothing has been deployed, and nothing was written to production.

## 1. Executive summary and release recommendation

**Release recommendation: Do not ship yet. Ship with known risks once the five gates below are met.**

- The code fixes on this branch close all five High findings that code can fix:
  - A retry could send a transaction twice (RT-1).
  - An ambiguous Perpl outcome could be retried into a duplicate order (RT-3, RI-2).
  - A comma decimal made "0,5" sign 5, on both iOS and web (UI-1, GN-1).
- They also close most of the Medium findings in reach of code. Examples:
  - The web swap trusted Kuru Flow's API response for its target and value (WEB-1).
  - Email & Password wallets had no key export (IOSK-1).
  - Sign Out deleted an imported key while telling the user it was safe (IOSK-3).
  - A stale quote could be signed (RT-4, RW-1, RW-4, UI-2).
  - Edge functions made unthrottled calls to the Privy admin API (SB-3).
  - The first 7 migrations were missing, so the backend could not be rebuilt from source (OH-9).

The two remaining High findings are custody problems, not code problems, and only the owners can close them.

- **SEC-1:** the governance/owner key for the live contracts is held in plaintext in a `.env` file and passed on the command line.
- **OH-1:** every v2 Email & Password wallet depends on one server key (`email_pepper_key` in Supabase Vault) that has no escrow or backup. If that key is lost, those wallets become unrecoverable except through the in-app export this branch adds.

Gates before release:
1. **Build and test the app in Xcode.**
   - No Swift compiler was available in the audit environment. Every Swift change was checked by a syntax-level differential parse (0 regressions across 164 files) and by two independent code reviews, not by a compiler.
   - A reviewer found one compile error, now fixed in `180755b`. Run `DyorKit` tests and a device build before shipping.
2. **Deploy the backend fixes:**
   - Edge Functions `wallet-auth`, `email-rebind`, `delete-account` and `pin-media`.
   - Migration `23_default_privileges_least_privilege.sql`, applied as `postgres`.
   - The web app and worker, from this branch.
3. **SEC-1:** move governance to a hardware wallet or a Safe, and delete the plaintext key.
4. **OH-1:** escrow the email pepper key (KMS/HSM plus an offline backup), and write down the recovery procedure.
5. **LR-1 / LR-2:** publish a privacy policy and the Terms page the app already links to. The App Store requires a privacy policy link.

After these five gates, the remaining Open items are Medium or lower. Most are accessibility, UX consistency and reliability work (§10). No Critical finding was found.

Three contract findings stay live until a redeploy, because the deployed contracts are immutable. Each has a keeper mitigation that needs no redeploy (§3):
- **MO-1:** Moments graduation can be griefed. A proof of concept is on this branch.
- **LP-1:** Monday graduation can be blocked.
- **LP-2:** pool fees accumulate unswept.

## 5. High and Medium findings (full detail)

### GN-1 · High · Fixed — parseAmount strips every comma, so a decimal comma signs 10x-1000x the typed amount in Send, Swap, Launchpad buy/sell, dev buy, Perpl deposit/withdraw and the Moments price

- **Category:** Reliability · **Repo:** IOS-app · **Verification:** 3/3 verifier(s) upheld it (finder rated High)
- **Confidence:** Confirmed
- **Location:** app/lib/format.ts:33-41 (parseAmount); callers app/page.tsx:166-179 (SendSheet), app/swap/page.tsx:95,149, app/launchpad/token-panels.tsx:37,59, app/launchpad/create/page.tsx:68, app/perps-screen.tsx:75-83,183, app/moments/create/page.tsx:36,76
- **Issue:** parseAmount removes every ',' before validating, so a comma typed as a decimal separator becomes part of the integer. '0,5' becomes '05' = 5, '1,5' becomes 15, '0,05' becomes 5 (100x) and '0,001' becomes 1 (1000x). I ran the function against the installed viem 2.56.3 and it returned exactly these values. Every amount input uses inputMode="decimal". On iOS Safari that keypad has a single separator key that follows the device region, which is ',' in most of Europe and Latin America, so comma-locale phone users can only type the wrong form. Trace of each flow: (1) SendSheet: the parsed value becomes the native `value` or the ERC-20 `transfer` amount. The only guard is parsed <= balance, and the tx label and success toast show the RAW text ('Send 0,5 MON' / 'Sent 0,5 MON'), so nothing in the app shows 5. (2) Swap: amountIn = parseAmount(...) is swapped. The input still shows '0,5' while 'You receive' shows 10x output; only the post-click TxStatus label shows the parsed 5. (3) Launchpad TradePanel: buy spends 10x the pair asset (the button just says 'Buy $SYM'); sell sells 10x the tokens. (4) Launchpad create: devBuy is 10x. The button label does show the parsed amount ('Launch for X MON + 5 MON'). (5) Perpl collateral: deposit approves and deposits 10x AUSD, and withdraw withdraws 10x. Labels show the raw text ('Deposit 0,5 AUSD'). (6) Moments create: the immutable collect price becomes '0,50' -> 50 USDC (100x). The preview shows the parsed '$50'. Perps size and limit price use Number(), so '0,5' becomes NaN -> 0 and the button is disabled with no reason given (no wrong amount). Creator tax and allocation are rejected with a visible error (safe). Separately, viem's parseUnits ROUNDS extra fraction digits half-up instead of throwing: '0.1234567' USDC becomes 0.123457, and '0.0000004' USDC becomes 0, which silently disables Send. The lead's 'silent null' description is therefore not accurate: the result is silent rounding.
- **Impact:** Irreversible over-sends to third parties: a comma-locale user who types 0,5 MON in Send and holds at least 5 MON transfers 5 MON, and the app confirms 'Sent 0,5 MON'. Swaps, launchpad buys, dev buys and Perpl deposits run at 10x, 100x or 1000x the intended size with matching price impact, fees and exposure. A Moments price is fixed on-chain at 10x or 100x forever. The only remaining safeguard is the external wallet prompt showing the real value, which many users skim.
- **Recommended fix:** Change parseAmount only; every caller then benefits. (a) Apply input.normalize('NFKC') so full-width digits are accepted. (b) If the string has no '.' and exactly one ',', treat the comma as the decimal separator (this is what mobile decimal keypads emit). If the digits after that comma are exactly three (e.g. '1,234'), the input is ambiguous: return a distinct 'ambiguous' result and show 'Use a dot for decimals' rather than guessing. (c) Only strip commas when the whole string matches strict en-US grouping /^\d{1,3}(,\d{3})+(\.\d*)?$/; otherwise reject. (d) Reject inputs with more fraction digits than `decimals` instead of letting viem round. Change the labels to show the parsed amount: app/page.tsx:171/179 and app/perps-screen.tsx:77/83 should use fmtUnits(parsed/amt, decimals) instead of the raw `amount`/`collatAmount`. Replace Number(size)/Number(price) in perps-screen.tsx:58-59 with the same parser, scaled by lotDecimals and priceDecimals. Behaviour change: pasting '1,234' no longer means 1234. It is flagged instead, and it can never turn into a larger amount.
- **Status:** Fixed — ba7e37d

### RI-2 · High · Fixed — Perpl one-click orders: an ack timeout or a failed TP/SL frame reports the whole order as failed, and the enabled button places another entry

- **Category:** Reliability · **Repo:** IOS-app · **Verification:** 3/3 verifier(s) upheld it (finder rated High)
- **Confidence:** High Confidence
- **Location:** ios/DyorKit/Sources/DyorKit/Services/Perpl/PerplTradeClient.swift:317-327 (placeAll), 342-356 (send); ios/DyorHQ/Wallet/PerplTrading.swift:458-490 (submitBracket); ios/DyorHQ/Perps/PerpTradeView.swift:2108, 2126-2172 (AuthedOrderSheet.place)
- **Issue:** The WebSocket order frame is written with send errors ignored (`task?.send(...) { _ in }`). Each frame's ack is awaited with an 8 s timer that throws PerplTradeError.timeout ('Perpl did not acknowledge the order in time.'). A socket close throws PerplTradeError.closed. placeAll sends the entry, then the TP and SL frames, each with `try await`. So after the entry is ACCEPTED, a timeout or socket drop on a trigger frame throws out of placeAll, and the accepted entry ack is discarded. AuthedOrderSheet.place catches any error and sets `.failed(describe(error))`. The Long/Short PrimaryButton stays visible and enabled (`isBusy: phase == .placing` only). Tapping it again calls submitBracket, which takes a fresh `client.nextRequestId()`, so nothing on Perpl's side deduplicates the second entry. In the failure path, TriggerStore and Activity are also never written.
- **Impact:** The user can open a second leveraged position of the same size. In the bracket case the first position is already open, and the app has told the user the order failed and recorded no TP/SL for it. The first entry's triggers may have been dropped, so that position can also be unprotected without the user knowing. Doubled leveraged exposure is a realistic fund-loss path. It needs an ack timeout or a socket drop right after a frame is written: poor mobile network, app suspension, or a Perpl gateway hiccup.
- **Recommended fix:** 1. In placeAll, stop throwing once any frame has been acked. Catch errors on later frames and return the acks gathered so far, with each remaining trigger marked unknown (for example, have BracketResult carry `Bool?` per trigger plus the error). Then place() can show `.doneWarning("Position opened; take-profit/stop-loss status unknown — check Orders")`. 2. When the entry frame itself times out or the socket closes after the write, add an `.unknown` phase instead of `.failed`. That phase hides the Place button, refreshes openOrders and on-chain positions, and tells the user to check before placing again. 3. Use the completion handler of URLSessionWebSocketTask.send to fail fast with a 'not sent' error when the write itself fails. Only that case can be safely offered as a retry. 4. Optionally reuse the same entry requestId on a same-sheet retry, so Perpl's strictly increasing rq check rejects a duplicate. Confirm Perpl's rq/lfr semantics first.
- **Status:** Fixed — 5ef8302 + 334d648

### RT-1 · High · Fixed — Retrying a failed confirmation re-sends transactions that were already broadcast, causing duplicate swaps, sends, buys, launches and deposits

- **Category:** Reliability · **Repo:** IOS-app · **Verification:** 3/3 verifier(s) upheld it (finder rated High)
- **Confidence:** Confirmed
- **Location:** ios/DyorHQ/Wallet/TransactionRun.swift:22-45,138-140 (TransactionRun.start / ConfirmationSheet); ios/DyorKit/Sources/DyorKit/Chain/Transactions.swift:232-264 (TransactionSender.run); ios/DyorKit/Sources/DyorKit/Core/RPCClient.swift:266-273 (waitForReceipt). Affects every ConfirmationSheet flow plus ClosePositionSheet/AddMarginSheet (PerpTradeView.swift:1896-1900, 2000-2004) and BridgeModel.execute (BridgeModel.swift:416)
- **Issue:** The runner keeps no record of which steps it already broadcast. Once a transaction is sent, a later error puts the sheet in `.failed`, and that error can be (a) any single failed receipt poll (transport error, all endpoints 429 or 5xx, malformed response), (b) the 90 s receipt timeout, or (c) a failure in a later step of the plan. In `.failed` the Confirm button is enabled again with the same label. Tapping it runs `run.start(steps…)` again, which clears the progress list and executes the whole plan from step 0. Approval steps are skipped when the allowance already covers them, but every `.call` step (swap, ERC-20/MON transfer, curve buy/sell, launch, Perpl deposit/withdraw, Moments publish, passkey collect) is signed again with the next pending nonce and broadcast a second time. Nothing checks whether the first hash landed. The Bridge has the same problem at broadcast time. Non-Monad source chains use a single-URL RPCClient (AppEnvironment.swift:94), so a lost `eth_sendRawTransaction` response shows as `.failed`. "Try again" then re-quotes and sends a new deposit.
- **Impact:** Real funds are spent twice: a second swap of the same size, a second send to the recipient, a second curve buy, a second token launch (launch fee paid again), or in TransferSheet a second MON→AUSD swap before the deposit. The trigger is ordinary mobile conditions: a brief connectivity drop, switching apps while the receipt is polled (the suspended URLSession task fails on resume), or public-RPC throttling. The UI encourages the retry: the progress list still says "<step> sent", the error reads "The network connection was lost." or "The transaction was sent but has not been confirmed yet.", and the primary button says "Swap" / "Send" / "Buy".
- **Recommended fix:** 1) In TransactionRun, track which steps were sent and which confirmed (step index to hash). If an error arrives after any hash was sent but before its receipt, enter a new non-retryable phase such as `.unconfirmed(hash)`. It shows "Sent, waiting for confirmation", an explorer link and a "Check status" action that only re-polls `waitForReceipt(hash)`, with no Confirm button. 2) When a later step fails before it is broadcast (a simulation revert, a cancelled passkey prompt), resume from the first step that was not sent instead of re-running confirmed `.call` steps. 3) Make `RPCClient.waitForReceipt` tolerate transient errors: catch NetworkError and rate-limit RPCError inside the loop and keep polling until the deadline. Before throwing `timedOut`, compare `eth_getTransactionCount(latest)` with the prepared nonce to detect a transaction that landed or was replaced. 4) Bridge: when `send` throws a transport error, read the source-chain nonce before offering "Try again". Behaviour change: after a post-broadcast network error, users get a status check instead of an immediate re-confirm. Pre-broadcast failures stay retryable.
- **Status:** Fixed — 5ef8302

### RT-3 · High · Fixed — Perpl one-click order ack timeout or socket close is shown as a retryable failure, and a retry sends a new order

- **Category:** Reliability · **Repo:** IOS-app · **Verification:** 3/3 verifier(s) upheld it (finder rated High)
- **Confidence:** High Confidence
- **Location:** ios/DyorKit/Sources/DyorKit/Services/Perpl/PerplTradeClient.swift:343-350 (send), 369-382 (receive failure); ios/DyorHQ/Wallet/PerplTrading.swift:458-490 (submitBracket); ios/DyorHQ/Perps/PerpTradeView.swift:2108-2110, 2125-2172 (AuthedOrderSheet.place)
- **Issue:** `PerplTradeClient.send` writes the order frame to the socket first and then waits 8 s for the ack. On timeout it throws `PerplTradeError.timeout`. If the socket fails meanwhile, every pending continuation gets `.closed`. In both cases the frame may already have been accepted and forwarded by Perpl. `AuthedOrderSheet.place` treats either error like a rejection: `phase = .failed(describe(error))`, and the primary "Long/Short" button is enabled again. A retry calls `submitBracket` again, which allocates new strictly-increasing request ids through `client.nextRequestId()`, so Perpl cannot recognise the retry as a duplicate. Nothing reconciles against `perplTrading.openOrders` or positions before the retry is allowed.
- **Impact:** A late ack under gateway load, or a dropped connection during placement, followed by the natural "try again" opens a second leveraged position of the same size, possibly with a second set of TP/SL triggers. This is direct exposure to double the intended risk.
- **Recommended fix:** Separate "rejected" from "outcome unknown". When `submitBracket` throws `.timeout` or `.closed` after `placeAll` started, set a non-retryable phase such as `.unknown` ("Checking whether your order went through…"). Then reconcile: wait for the socket to reconnect and inspect the mt:23/24 `openOrders` snapshot and `model.load` positions or fills for the market. Offer a new submission only if no matching order or position change exists. Optionally keep the entry's request id and reuse it on a retry, so Perpl's strictly-increasing rq rule rejects a duplicate; confirm that Perpl behaves this way first. Behaviour change: an ambiguous timeout no longer gives an instant retry.
- **Status:** Fixed — 5ef8302

### UI-1 · High · Fixed — A comma decimal is silently dropped from token amounts ("0,5" parses as 5), so comma-locale users sign 10x–100x the intended amount; the Launch review even echoes the raw text

- **Category:** Reliability · **Repo:** IOS-app · **Verification:** 3/3 verifier(s) upheld it (finder rated High)
- **Confidence:** Confirmed
- **Location:** ios/DyorKit/Sources/DyorKit/Core/Format.swift:25-28 (Amount.parse), used by ios/DyorHQ/Design/Components.swift:177-178 (AmountField); SendSheet ios/DyorHQ/Profile/ProfileView.swift:269; SwapModel ios/DyorHQ/Swap/SwapView.swift:380; Launch a Coin ios/DyorHQ/Launchpad/LaunchpadView.swift:794,889; Launchpad trade LaunchpadView.swift:388; Bridge ios/DyorHQ/Bridge/BridgeModel.swift:269; Perps deposit ios/DyorHQ/Perps/PerpsView.swift:165; Transfer ios/DyorHQ/Home/TransferSheet.swift:32; Moments price ios/DyorHQ/Moments/CreateMomentView.swift:47; fail-silent variants SwapView.swift:548 (custom slippage) and ios/DyorHQ/Wallet/PriceAlerts.swift:139
- **Issue:** Every token-amount field uses `.keyboardType(.decimalPad)`. In any region whose decimal separator is a comma (DE, FR, ES, IT, NL, BR, most of LatAm, plus anyone who set Number Format to 1.234,56), the pad's only decimal key is ",". The codebase already acknowledges this at PerpTradeView.swift:2226. `Amount.parse` treats "," as a thousands separator and deletes it: "0,5" becomes "05" = 5, "0,05" becomes 5 (100x), "1,25" becomes 125. Only the Perps ticket has a locale-aware parser (`perpDouble`). Every other money field goes through `Amount.parse`: Send, Swap, Launchpad buy/sell, the Developer Buy on Launch a Coin, Bridge, Perps deposit/withdraw, Home Transfer and the Moments collect price. CreateMomentView even handles the comma for the allocation field on the next row (line 49) but not for the price field (line 47). The guards differ by flow. Send, Swap, Perps and Launchpad show the parsed amount in their review sheet, which is the only safeguard. Bridge has no review sheet: the PrimaryButton calls `model.execute()` directly, and the field keeps showing "0,5". Launch a Coin's review prints `initialBuyText` verbatim ("Developer buy 0,5 MON") while `LaunchInput(initialBuy: initialBuy)` carries the parsed 5 MON into `value: launchFee + input.initialBuy`, so the review misstates what is signed. The custom slippage field and the price-alert target use `Double(text)`, which returns nil for "0,3". Those fail silently: slippage keeps the previous value while the field shows 0,3, and the alert's Add button stays disabled with no reason given.
- **Impact:** For users in comma-decimal regions, any fractional amount is multiplied by 10^(number of fraction digits typed). If the balance covers the inflated amount, the user can broadcast a wrong on-chain transaction: sending 10x to an external address is irreversible; buying 10x on a bonding curve or bridging 10x cross-chain realises fees, tax and slippage. Bridge and the Launch developer buy give no accurate readback of the amount before signing. If the balance does not cover it, the flow just breaks ("Insufficient MON" / disabled Review) and the user cannot enter a fractional amount at all. This is a core flow breaking for a large share of users, with realistic fund loss.
- **Recommended fix:** 1) Add one locale-aware entry parser in DyorKit, e.g. `Amount.parse(_:decimals:locale: Locale = .current)`. If the input contains only the locale's decimal separator ("," in de/fr), treat it as the decimal point. Keep "." always valid as a decimal, because Max/percent writers emit POSIX via `Amount.exact`. Strip the grouping separator only when the other separator is also present ("1.234,5" / "1,234.5"). Return nil for ambiguous or multiple-separator input rather than guessing. Keep the existing en_US test ("1,234.5" → 1234.5) and add de_DE cases ("0,5" → 0.5, "1,25" → 1.25). 2) Route `perpDouble`, SlippageSheet, PriceAlerts and CreateMomentView through it, so there is one parser. 3) Optionally normalise in AmountField's binding ("," to "." when the locale decimal is ",") so the field shows exactly what is parsed. 4) LaunchpadView:889: show `NumberStyle.units(initialBuy, decimals: pairInfo?.decimals ?? 18)`, never the raw text. 5) Bridge: add a "You send <parsed amount> <symbol>" row to the summary card, or a review step. This changes behaviour only for comma-locale users, whose input currently mis-parses; en_US input is unchanged.
- **Status:** Fixed — ba7e37d

### OH-1 · High · Owner action — Every v2 email+password wallet depends on one un-escrowed server key (Supabase Vault 'email_pepper_key'), and there is no restore runbook and no way for users to export their key

- **Category:** Ops · **Repo:** IOS-app · **Verification:** 3/3 verifier(s) upheld it (finder rated High)
- **Confidence:** High Confidence
- **Location:** supabase/migrations/20_email_pepper.sql:27-33,83-86; ios/DyorKit/Sources/DyorKit/Chain/EmailWallet.swift:8-13; ios/DyorHQ/Wallet/WalletExportView.swift:41-49; ios/DyorHQ/Profile/AccountDeletion.swift:198-199; dyorhq/docs wallet/export-sign-out-delete.md:22,34
- **Issue:** A v2 wallet's private key is HKDF(S || p), where p is an HMAC under key K. K exists only as a Supabase Vault secret inside project fmnjqrguvopusfufmirs. The migration's only DR statement is that K 'is covered by this project's Supabase backups / PITR'. Nothing in the repo shows that the plan has backups or PITR, K is not escrowed off-platform, and no document explains how to restore it. Vault ciphertext is encrypted with a project-specific root key, so a logical dump restored into another project very likely cannot decrypt K (to verify with Supabase). The key-check value makes a lost K fail closed: the service refuses and never re-derives. Users have no escape hatch of their own. This only changes what comma-locale users see.
